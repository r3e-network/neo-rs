The crate is split into two feature-gated subsystems under `src/`: `server` (feature `server`, optionally enhanced with `jsonrpsee-server`) and `client` (feature `client`).

- **Server side** (`src/server/`): `rpc_server.rs` defines the `RpcServer` struct that owns a `NeoSystem`, handler registry, session store, optional TLS config, and WebSocket bridge. Each RPC domain (blockchain, node, state, wallet, oracle, tokens_tracker, application_logs, utilities) lives in its own `rpc_server_*` module and registers handlers via `rpc_handler` / `protected_rpc_handler` helpers built on `RpcMethodDescriptor`. A global `SERVERS` registry in `rpc_registry.rs` holds per-network `Arc<RwLock<RpcServer>>` instances. HTTP routing is implemented with `warp` in `routes/` (CORS, basic auth, rate limiting, batch handling, depth limits), while an optional `jsonrpsee_adapter.rs` provides a jsonrpsee module wrapper. WebSocket subscriptions are isolated in `ws/` (bridge, events, handler, subscription manager). Middleware includes a `rate_limiter` using `governor` + `dashmap`.
- **Client side** (`src/client/`): `rpc_client/mod.rs` exposes `RpcClient` and `RpcClientBuilder` backed by `reqwest`, plus typed API modules `nep17_api`, `wallet_api`, `policy_api`, `state_api`, `contract_client`, and `utility`. Shared request/response models live in `client/models/` (one file per RPC type, e.g. `rpc_block.rs`, `rpc_transaction.rs`, `rpc_response.rs`). Transaction construction helpers are in `client/utility/` (attributes, witness, nep parsing).
- **Shared layer**: `error.rs`, `error_code.rs`, and `serialization.rs` provide common error types, JSON-RPC error codes, and serialization helpers used by both sides.
- Dependency direction: server depends on `neo-core` (via `NeoSystem`, `Wallet`, `services::RpcService`); client depends on `neo-config` and `neo-json`; both share `neo-primitives`, `neo-crypto`, `neo-io`. The crate root re-exports only public entry points through `lib.rs` gated by features.
