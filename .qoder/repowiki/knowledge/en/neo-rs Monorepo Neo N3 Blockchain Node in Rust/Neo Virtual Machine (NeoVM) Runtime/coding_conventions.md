- Opcode handlers are implemented as `fn(&mut ExecutionEngine, &Instruction) -> VmResult<()>` function pointers stored in a fixed-size 256-entry array inside `JumpTable`, with each category module registering its handlers via a `register_handlers` function called from `register_default_handlers`.
- Vendored core modules (`vm`, `abi`, `interpreter`, `runtime`, `host`) are kept private and their public surface is re-exported through `lib.rs` to preserve the previous external crate's API shape for downstream consumers.
- Unsafe host callbacks are funneled through the `HostPtr` wrapper in `execution_engine/mod.rs`, which encapsulates the raw `*mut dyn InteropHost` pointer and exposes typed methods like `on_context_loaded`, `pre_execute_instruction`, and `invoke_syscall`.
- Error propagation across all fallible VM operations uses the `VmResult<T>` alias returning `VmError`, with invalid opcodes routed through `JumpTable::invalid_opcode` rather than panics.
- Category-scoped opcode groups are split into sibling files under `jump_table/` (e.g. `bitwisee.rs`, `numeric.rs`, `control.rs`) mirroring the C# `JumpTable.*.cs` layout, each exporting a `register_handlers` entry point.
- Interpreter executor code is partitioned by opcode family into `executor/{push_ops,numeric_ops,compound_ops,control,slot_ops,stack_ops,result_ops}.rs`, keeping each handler type in its own file.
