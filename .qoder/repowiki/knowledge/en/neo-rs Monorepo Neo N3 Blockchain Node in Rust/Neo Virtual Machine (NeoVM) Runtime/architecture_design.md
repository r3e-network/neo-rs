The crate is organized as an adapter-oriented VM with clear layering. The vendored core lives under `vm/` (opcode definitions, instruction parsing, limits, graph analysis, exception handling) and `abi/` (stack value types, codecs), exposing canonical bytecode semantics. The stateful host surface sits on top: `execution_engine/` owns the `ExecutionEngine` struct that holds the invocation stack of `ExecutionContext`s, `EvaluationStack`, `ReferenceCounter`, `InteropService`, and a `HostPtr` wrapper around a raw `*mut dyn InteropHost` callback into the parent `ApplicationEngine`. `interpreter/` provides the low-level interpreter API (`interpret*` functions) plus executor submodules grouped by opcode category (`push_ops`, `numeric_ops`, `control`, `slot_ops`, etc.) and helper/state modules (`call_frame`, `try_frame`). `jump_table/` implements a fixed-size `[Option<InstructionHandler>; 256]` dispatch table whose default handlers are registered per category (`bitwisee`, `compound`, `control`, `numeric`, `push`, `slot`, `splice`, `stack`, `types`) and which the engine calls in its hot loop. `semantics/` contains pure ABI-level operations (arithmetic, collections, comparison, conversion, splice, stack shape). `stack_item/` defines the native `StackItem` enum and compound types; `execution_context/` models call frames with locals/static fields; `host/syscall.rs` and `interop_service.rs` define the SYSCALL boundary. Top-level `lib.rs` re-exports both the vendored core surface and the neo-rs host types, making the crate self-contained for `neo_core`.
