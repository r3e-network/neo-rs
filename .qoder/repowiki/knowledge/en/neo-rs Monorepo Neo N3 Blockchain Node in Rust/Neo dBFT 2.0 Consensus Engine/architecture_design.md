The crate is organized as a layered state machine around `ConsensusService` (`service/core.rs`) which owns a `ConsensusContext` (`context/mod.rs`) tracking view number, validator set, signatures, proposed block data, and message caches. The service exposes an event-driven API via `ConsensusEvent` and `ConsensusCommand` (`service/types.rs`) and dispatches incoming messages through per-flow handlers in `service/handlers/{prepare,commit,change_view,recovery}.rs`, each backed by shared helpers in `service/helpers/` (dbft payload hashing/signing, block assembly, signature aggregation, time). Message types are defined under `messages/` (PrepareRequest, PrepareResponse, Commit, ChangeView, RecoveryRequest/Message) implementing a common `ConsensusMessage` trait and wrapped in a `ConsensusPayload` envelope that serializes to the Neo N3 DBFTPlugin on-wire format `[type:1][block_index:4][validator_index:1][view_number:1][body...]`. Cryptographic signing is abstracted behind the `ConsensusSigner` trait (`signer.rs`), allowing pluggable HSM/wallet backends while the default path uses in-process secp256r1 keys wrapped in `Zeroizing`. Persistence of round state is handled via a `PersistedConsensusState` struct (serializable with serde) enabling crash recovery. Dependencies flow inward: service → context + messages + helpers; messages depend only on primitives/crypto; no upward dependencies on higher layers.
