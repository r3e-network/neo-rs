# Neo-rs 事故响应手册（真实风险场景）

> **日期**：2026-09-19
> **协议基线**：Neo N3 v3.10.1
> **文档定位**：针对本项目的**真实风险场景**编写响应流程。每场景包含：检测信号、响应步骤、回滚/安全伞、升级路径、责任人角色、事后复盘。
> **诚实声明（必须前置阅读）**：本手册所有场景的响应有效性，都受限于一个事实——**本项目对"存储语义、原生合约价值转移、完整区块状态一致"尚无机器验证证据**（`DEPLOYMENT.md` §3 S1/S2/S6）。因此当场景触发时，**默认假设"本节点状态可能与其他参考节点不一致"**，绝不以其状态作为权威/分叉裁决依据。

---

## 0. 通用原则

- **怀疑优先**：任何状态异常，默认两侧不一致，先隔离再下结论。
- **证据保全**：事故期间立即冻结并导出：日志、`/metrics` 快照、配置、`getblockcount`/`getblock` 哈希链、区块/交易哈希。这些是复盘的唯一可信依据。
- **C# runner 是验证工具**：`tools/csharp-*` 仅用于事后差异比对，**不参与**生产节点运行时，也不用于在线裁决。
- **回滚安全伞**：所有响应均以"停止节点、保留数据、回滚二进制、从备份或重同步恢复、再与参考网络交叉校验"为安全伞。
- **角色**（示例，可按组织替换）：
  - **IC（Incident Commander）**：总指挥，唯一决策人。
  - **Ops**：节点运维，执行启停/备份/回滚。
  - **Protocol/Verification**：负责差异验证复跑与语义研判。
  - **Security**：负责密钥/审计/对外披露。
  - **Postmortem Owner**：负责事后复盘与整改。

## 场景 1：与 C# 参考产生状态不一致 / 分叉痕迹

**触发场景**：本节点 `getblockcount`/区块哈希与主流（或多节点）不一致；出现未被主流确认的分叉块；state root 无法对齐。

### 检测信号
- `getblockcount` 长时间落后或超前；`/healthz` 头部延迟升高。
- 与其他可信节点对比区块哈希（同高度）不一致。
- 日志出现区块校验失败、view change 异常、MPT/state root 报错。
- 监控：区块哈希差异告警（需运维配置对拍）。

### 响应步骤
1. **隔离**：将节点从出块/对外 RPC 摘除，暂停其参与共识或停止同步，避免污染。
2. **证据冻结**：导出日志、metrics、config、当前链头哈希与最近 N 块哈希、以及触发时刻的差异上下文。
3. **初判**：区分"本节点已分叉"vs"网络共识在演进（view change/重排）"。用第二独立参考源（官方 seed、另一 C#/参考节点）对拍。
4. **Verification 复跑差异验证**：对出现分歧的区块/交易脚本，用 G1-G4 向量或针对性向量复跑 Rust↔C# v3.10.1。
5. **定位语义层**：分歧若在 VM 指令 → G1/G2；wire 字节 → G3；syscall/原生/存储 → **明确属于未覆盖盲区（S1/S2/S6）**，默认原因未知，需专项调查。
6. **裁决**：在盲区未澄清前，**不得**宣称任一侧正确；以参考网络高度为回滚/重同步基准。

### 回滚 / 安全伞
- 停止节点 → 保留数据目录副本 → 回滚到已 PASS 的已知版本 → 从参考链高度**重同步**（不清除审计日志）。
- 若数据疑似损坏：从备份恢复（见 `COMPLIANCE.md` §3）或全量重同步。
- 恢复后必须与参考网络交叉校验链头哈希一致后才放行。

### 升级路径
- 修复语义 → 重新生成证据 → 在隔离测试网/私有网重放触发区块 → 全量 G1-G4 + Coq 门禁 → 灰度放行。

### 责任人
- IC（裁决）、Ops（隔离/回滚/重同步）、Protocol/Verification（差异复跑与语义定位）、Postmortem Owner（复盘）。

### 事后复盘要求
- 记录：触发高度/哈希、差异向量、两侧结果、根因分类（VM/wire/syscall/存储/盲区）、修复与验证证据、遗留盲区清单。

## 场景 2：coinbase / 存储异常

**触发场景**：原生合约（NEO/GAS）余额、`totalSupply`/`balanceOf`、coinbase 分发、存储键值出现异常。

### 检测信号
- 余额/供应量对拍异常；`balanceOf` 与参考网络不一致。
- 存储读/写报错、MPT 节点校验失败、state root 计算偏差。
- 与区块应用相关的 gas/fee 收敛偏离参考。

### 响应步骤
1. **隔离**：若在共识节点，立即摘除出块/投票权，转入只读观测。
2. **证据冻结**：导出触发交易的脚本、执行轨迹、前后存储 diff、gas 消耗。
3. **重点研判**：**本项目对原生合约含存储读的方法（`totalSupply`/`balanceOf`/`transfer`）与存储 Get/Put/Delete/Find 正路径均未验证（S1/S2）**。此类异常**必须**视为"盲区内的未验证语义可能被触达"，不假设实现正确。
4. **差异复跑**：构造覆盖该交易的原生/存储对齐向量（需在两侧种入相同 genesis/部署态——当前 C# 侧未种 NEO/GAS ContractState，属已知未对齐项，见 syscall 报告 §2.2）。
5. **隔离根因**：区分"存储语义差异"vs"原生解析路径差异"vs"应用逻辑 bug"。

### 回滚 / 安全伞
- 立即停止应用该异常交易后的任何出块/签名行为。
- 保留数据 → 回滚版本 → 从备份或参考链高度重同步 → 与参考对拍余额/state root。
- 若已广播异常状态，按参考网络为准回滚本地，不向网络传播非标准状态。

### 升级路径
- 补齐存储/原生正路径差异验证 → 修复 → 私有网重放 → G4 对齐集扩展 → 灰度。

### 责任人
- IC、Ops（隔离/重同步）、Protocol/Verification（原生/存储向量构造与复跑）、Security（若涉资金外泄）。

### 事后复盘要求
- 记录盲区触达点、是否命中 S1/S2 未覆盖语义、验证补齐建议、资金影响评估（如适用）。

## 场景 3：共识节点宕机 / 隔离

**触发场景**：共识节点进程崩溃、网络分区、长时间无响应；dBFT 触发 view change / 丢失出块参与。

### 检测信号
- 进程退出/反复 panic；`/healthz` 不响应；出块参与率下降；大量 view change。
- 网络分区（连接数骤降、与其它 validator 断连）。
- `LimitNOFILE`/内存/磁盘告警。

### 响应步骤
1. **确认**：区分"单节点故障"vs"网络级分区"。检查监控、连接、进程状态。
2. **快速拉起**：若是进程崩溃，按重启策略拉起；检查启动日志是否有校验/存储报错。
3. **若反复崩溃**：停止自动重启，保留 core dump/日志，进入 root-cause 调查（不复用 `pkill -9` 破坏证据）。
4. **共识层应对**：本节点缺席时，网络由其余 validator 的 view change 机制自愈；本节点**不得**在未对齐状态强行出块。
5. **数据完整性**：重启后校验链头与参考一致；若状态对不上，走场景 1/2 的隔离+重同步流程。

### 回滚 / 安全伞
- 停止 → 回滚二进制 → 从备份/参考高度重同步 → 校验链头哈希 → 重新注册参与共识。
- 若涉及共识私钥异常（如签名不一致被网络拒绝），Security 介入评估密钥轮换。

### 升级路径
- 高可用：多实例、自动故障转移、健康探针、告警阈值；缺失时提升监控覆盖。

### 责任人
- IC、Ops（拉起/回滚/重同步）、Security（密钥异常时）、Postmortem Owner。

### 事后复盘要求
- 根因（代码/资源/网络/配置）、恢复时长、RPO/RTO 实测、宕机期间的出块缺席影响。

## 场景 4：验证门禁发现语义分歧

**触发场景**：差异验证（G1-G4）或 Coq 门禁（G5）在 CI/发布流程中**新发现**与参考 v3.10.1 不一致，或某个 Coq 模型由通过转未通过。

### 检测信号
- `vm-diff.py` 返回 exit 1（出现 different 向量）。
- `serdiff_compare.py` 返回 byte_compatible=false。
- `formal/ci/check_coq.py --all` 出现非全绿；新增 `Admitted`/`Axiom`。
- 版本升级/改动后回归出现分歧。

### 响应步骤
1. **立即冻结发布**：该 commit 禁止进入生产构建/部署候选，标记为 red。
2. **证据锁定**：记录差异向量、两侧结果、对应代码 commit、工具链版本（Coq/OCaml/C#/Rust）。
3. **分类**：是"真实语义分歧"还是"宿主/工具差异"（如 syscall 报告中的容器 hash、Policy 种子、native 解析路径）。
4. **溯源**：用 `git bisect`/diff 定位引入变更；对 Coq 模型核对是否新增伪命题/幽灵符号。
5. **处置**：真实分歧 → 修复实现或回退变更；工具差异 → 修正 runner/种子/容器构造并注明非语义分歧。
6. **回归验证**：修复后全量重跑 G1-G4 + Coq 门禁，登记新证据 SHA。

### 回滚 / 安全伞
- 未发布即拦截（最佳）；已发布 → 回滚该 commit → 回到上一 green 版本 → 重跑验证 → 再放行。
- 已上链受影响 → 转场景 1 隔离与重同步。

### 升级路径
- 加强门禁触发面：将 G1-G4 与 Coq 门禁接入 CI 预定子集，作为发布准入强制项。

### 责任人
- Protocol/Verification（分类与溯源）、IC（发布冻结/回滚决策）、Ops（生产回滚）、Postmortem Owner。

### 事后复盘要求
- 分歧性质、根因 commit、修复后证据、门禁是否应加强、是否需扩充向量覆盖盲区（S1/S2/S6）。

## 附录 A：盲区 × 场景对照（诚实提示）

| 盲区（`DEPLOYMENT.md` §3） | 可能触达的场景 | 当前验证状态 |
|------|------|------|
| S1 存储 Get/Put/Delete/Find 正路径 | 场景 2（存储异常）、场景 1 | **未覆盖** |
| S2 原生合约值转移 / genesis 原生态对齐 | 场景 2（余额/coinbase）、场景 1 | **部分覆盖，有真实解析差异** |

> **使用方式**：事故研判时，若异常落在上表任一盲区，即视为"无法用既有证据排除语义分歧"，必须走隔离+重同步+专项验证流程，不得以"实现已通过单元测试"作为免责依据。

## 附录 B：复盘模板（每场景通用）

1. 时间线（检测→响应→恢复→复盘）。
2. 检测信号来源与有效性。
3. 根因分类（协议语义 / 宿主差异 / 代码 bug / 运维 / 密钥 / 盲区触达）。

5. 证据完整度（日志/哈希/向量是否保全）。
6. 验证盲区是否被触达；新增验证待办。
7. 改进项（门禁、监控、流程、文档）。
8. 责任人与签收。
