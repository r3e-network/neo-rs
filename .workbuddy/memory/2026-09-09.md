## E2 完全解锁（fuzz libFuzzer C++，同日第四追加）

- **根因（上游缺口）**：libfuzzer-sys 0.4.10 build.rs **无 msvc/gnu 分支，glob 编译捆绑目录全部 .cpp**。`FuzzerExtFunctionsWindows.cpp` 无条件发 MSVC 专属 `__pragma(comment(linker, "/alternatename:..."))`（文件为 clang 预留了 `__builtin_function_start` 路径但 pragma 不分支），gnu 目标默认无 MS 兼容模式 → 20 个错误（约 7 个可选钩子 × 3）。`FuzzerExtFunctionsWeak.cpp` 被 `LIBFUZZER_LINUX/…` 守卫、Windows 上整体为空 → 无 weak 变体旁路。上游 LLVM CMake 在 mingw 下不编 Windows 变体，此组合上游从未测过。
- **解锁（零代码改动）**：`export CXXFLAGS_x86_64_pc_windows_gnullvm="-D_WIN32_WINNT=0x0A00 -fms-extensions"`——`-fms-extensions` 是最小开关：启用 `__pragma(comment(...))` 解析、**不定义 `_MSC_VER`**、不污染同目标其他 C++。实测单加这个就够，无需 `-fms-compatibility`。
- **链接实证**：lld 的 mingw 驱动（COFF 后端）**确实执行 `.drectve` 里的 `/alternatename`**——`cargo build` 链接 3 个 fuzz bin EXIT=0，若 alternatename 被忽略则 `LLVMFuzzerCustomMutator` 等可选钩子地址引用必成 undefined reference。
- **冒烟**：三个 target 各 5000 runs EXIT=0，无 crash、无 "Function not defined" 回退桩触发。`WARNING: no interesting inputs` 即预期证据：gnullvm host 无 sancov 插桩，libFuzzer 退化为盲变异——**覆盖引导 fuzzing 必须 Linux CI**（Rust sanitizer 不支持 windows-gnu/gnullvm，环境本质非代码缺陷）。
- 顺带：主工作区全默认成员 `cargo build`（dev profile）EXIT=0（7m08s），dev 构建级首测绿灯。
- **操作坑（本会话两次踩）**：Bash 工具工作目录**不跨调用持久化**，每次调用落回仓库根——`cd fuzz && cargo build` 下一条必须重新 `cd`，否则 `cargo build` 跑的是主工作区、相对路径 `../outputs` 落到 D:/ 下。cargo 输出日志 tee 用绝对路径。
