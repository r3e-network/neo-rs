# 2026-10-24 — 共识路径 panic 修复 + host 指针契约 + 死代码清理

## 真 bug：fast VM 结果栈转换 panic（`f21d3ff6`）

`apply_external_vm_halt` 用 `StackItem::try_from(value).unwrap()` 转换快速解释器的结果栈。脚本只要在栈上留一个 `Pointer` 就触发 panic，**5 字节脚本 `PUSHA 0` 即可**，脚本是攻击者可控的。

复现（把 Gorgon 激活高度钉到 0）：

```
thread 'pusha_pointer_on_result_stack_faults_instead_of_panicking' panicked at
neo-core\src\smart_contract\application_engine\external_vm.rs:343:45:
called `Result::unwrap()` on an `Err` value: InvalidOperation {
  operation: "Cannot convert Pointer(0) into neo-vm StackItem without host runtime identity" }
```

**可达性**：主网 Gorgon = 12,020,000（尚未激活），所以今天主网不可达；testnet 17,960,000、私有链、以及主网到达该高度后可达 → 确定性崩溃 = 全网停摆。

**修法不是 fault 而是重建指针**：`StackValue::Pointer(i64)` 只带偏移，`StackItem::Pointer` 还要所属脚本；快速解释器只跑当前 context 的脚本，所以用 `context.script_arc()` + `StackItem::from_pointer` 重建。C# `PUSHA` 本来就是 push `new Pointer(Script, offset)` 然后 HALT——**改成 FAULT 反而制造共识分歧**。`Interop`/`Iterator` 确实无 StackItem 对应物（且被 `script_uses_application_engine_host` 挡住），保持 fault；负偏移转 usize 失败也 fault。

同文件 `prepare_external_vm_execution` 的初始栈也有一处 `unwrap()`，改为 `.collect::<Result<_>>().ok()?` 回退到 fork-aware 解释器。

测试：`neo-core/tests/external_vm_stack_boundary_tests.rs`。

## host 指针：构造期 attach 是唯一必然产生悬垂指针的地方（`f14534e3`）

`attach_host()` 把 `&mut self` 转成 `*mut dyn InteropHost` 存进自己拥有的 `vm_engine`——自引用。原 SAFETY 注释写「the pointer remains valid for the engine's lifetime」，**假的**：`Ok(app)` 把引擎按值返回就移动了。

实际情况是每个执行入口都会重新 attach（`execute_allow_fault` / `execute_until_invocation_stack_depth` / `load_script_with_state`），已验证没有任何绕过这三处的 VM 执行路径。但两个构造函数在 `Ok(app)` **之前** attach，唯一效果就是留下一个悬垂指针。

处理：删掉两处构造期 attach（指针在首次使用前保持 `None`）、把三处注释改成真实不变量、同步修正 `HostPtr` 的 4 条不变量与 `unsafe impl Send` 的「the host moves with it」（裸指针不跟随移动）。

测试：`neo-core/tests/application_engine_host_pointer_tests.rs`——引擎装进 `Box` 后再跑 `System.Runtime.GetNotifications`（非 fast-path syscall，必须走 host 回调）。
