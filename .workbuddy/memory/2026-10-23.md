## benchmark-regression CI 长期红灯的根因（已修复，`aaea99cd`）

`cargo bench --workspace -- --save-baseline baseline` 把 criterion 参数传给了**每个 lib/bin 测试 harness**。它们不测任何东西，但会解析 argv：

```
error: Unrecognized option: 'save-baseline'
error: bench failed, to rerun pass `-p neo-config --lib`   (exit 101)
```

`set -euo pipefail` 因此在基线生成步骤中止 → step 11 失败、step 12/14 skip。`--no-fail-fast` 只让 cargo 继续跑其余目标，最终仍返回非零。

复现/反证：
- `cargo bench -p neo-config -- --save-baseline baseline` → 报错
- `cargo bench -p neo-config` → `0 passed; 0 failed; 14 ignored`，EXIT=0

修复要点：
- 从 manifest 解析 `[[bench]] harness = false`，生成 `-p <pkg> --bench <name>` 对（`serialization` 在 neo-core 和 neo-io 重名，必须带 `-p`）；
- 目标跑完没产出 `new/estimates.json` 就**失败**（防「0 benchmark 全绿」）；
- `neo-core` 的 `storage` bench 此前被 autobenches 以 libtest harness 运行，5 个基准**一个都没测**，已在 `neo-core/Cargo.toml` 声明 `harness = false`；
- 删除跨运行基线缓存，改为**同 job 两遍测量**（先记基线再对比）。criterion 报绝对墙钟，跨机器比较测的是机器差异；
- 阈值 20% + 绝对效应下限 10 µs。同代码三次连跑，`persist_block_one_ret_tx` 出现 +11.9% / 改善 / +22.1%，10% 阈值等于抛硬币；`block_persistence` 因此**移出闸门**，只作趋势；
- `--changed-since` 过滤历史 `change/` 目录；去掉递归删除（沙箱拒绝 bulk delete）；
- 实测：全套 38 min/遍，闸门 3m48s / 10 项 / 0 回归 / EXIT=0；变异测试 `--threshold 0.01 --min-abs-ns 0` → 91 条回归 / EXIT=1。

## 环境教训

- **编辑正在运行的 bash 脚本会破坏它**：bash 增量读取脚本文件，第 2 次闸门运行因此报 `unexpected EOF` 并给出 EXIT=2 的无效结果。跑长任务前先改完代码。
- 沙箱 safe-delete 会拦 `rm -rf target/criterion`（阈值 50 文件，实际 4987）。脚本里不能用批量递归删除，改 `cp -a src/. dst/` 合并。
- `argparse` 的 `epilog` 会把裸 `%` 当格式符：`10% threshold` 直接让 `--help` 崩在 `unsupported format character 't'`，必须写 `%%`。

## 新发现：clippy 闸门的 feature 盲区（已修 `7f350666`）

CI 的 clippy 不带 `--features`，所以 `neo-core` 的 rocksdb 生产后端从未被 lint。用同一组参数加 `--features rocksdb` 跑，报 **12 条 `clippy::all`**（全在 `persistence/providers/rocksdb/store.rs` 与 `write_batch_buffer.rs`：collapsible_if 与 filter_map→map）。

已全部改为 let-chain / `.map()`，无行为变化。修后：
`cargo clippy -p neo-core --features rocksdb --profile test -- -D clippy::all`（CI allow 列表）干净；`cargo test -p neo-core --features rocksdb --lib` **647 passed / 0 failed**；默认特性 clippy 仍 0 error。

**未加 CI lane**：用户明确在意 CI 时长，而 `--features rocksdb` 会触发 librocksdb-sys 的 C++ 构建，加一条 lane 代价明显。代码现在是干净的，将来若要加，命令已就绪。

## 同类缺陷第二处：14 个 repro 测试的路径解析（已修 `c495e512`）

`cargo test` 的 cwd 是**包目录**（`neo-core/`），所以 `NEO_REPRO_DB_PATH=data/Plugins/StateService/StateRoot` 解析成 `neo-core/data/...` 直接 panic：

```
open state root store: Io { ... failed to open RocksDB store at
data/Plugins/StateService/StateRoot: ... No such file or directory:
.../neo-core/data/Plugins/StateService/StateRoot/CURRENT }
```

而且 14 个文件有**两个互斥的默认值**（7 个 `data/Plugins/mainnet/StateRoot`、7 个 `data/mainnet/StateRoot`），本机**两个都不存在**——真实库是 `data/Plugins/StateService/StateRoot`（20 GB），也正是 `config/mainnet.toml` 与 validation workflow 的默认值。也就是说这些测试本地从来跑不了，文档给的命令还会崩。

改法：统一的 `common::repro_state_root_path()`——相对路径拼 repo root，无环境变量时按 `StateService/StateRoot` → `data/mainnet/StateRoot` → `data/Plugins/mainnet/StateRoot` 顺序探测。`NEO_CHAIN_DB_PATH` 同样处理。
