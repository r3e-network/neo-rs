## P2P 消息命令（本轮新增）

**23/23，名称与单字节判别符完全一致。** 判别符比名字更要紧——这些值直接上线，名字对而字节错会被所有其他节点拒收或误读。

Rust 侧**不是手写枚举**：`MessageCommand` 由 `p2p_message_command!` 宏生成，变体表在 `neo-primitives/src/macros.rs` 的 `__p2p_message_command_table`。提取必须**限定在该宏内**，否则会串进其他宏的条目。另外 `MessageCommand::Unknown(u8)` 来自 `protocol_enum_with_unknown!` 包装器，是保留未知字节的实现细节，**不是协议命令**，已排除。

## RPC 方法面：为什么不能说"对账完成"

**根因是上游没有可比基准。** Neo 的 RPC 服务**不在** `neo-project/neo` 主仓库（v3.10.1 树里没有服务端代码），而在 `neo-project/neo-modules`——该仓库 **2024-05-21 已归档**，**标签止于 v3.7.5，没有 v3.10.1**。

所以严格意义上，**v3.10.1 没有权威 C# RPC 方法清单**。用 `master` 比等于拿移动分支当基线，这与前面所有对账一律钉死 tag 的原则冲突，我没有这么做。

**指示性比对（基准 v3.7.5，跨 3 个次版本）**：

| 项 | 数 |
|---|---|
| C# v3.7.5 RPC 方法 | 42 |
| Rust 服务端注册方法 | 57 |
| **C# 有而 Rust 无** | **0** |
| Rust 有而 C# v3.7.5 无 | 15 |

多出的 15 个（`getproof`、`verifyproof`、`getstate*`、`getnep11*`、`getnep17*`、`findstates` 等）多数其实是 C# **v3.7.5 之后新增**的方法——"多余"主要反映**基准版本太旧**，而非 Rust 偏离。

**为什么不接入 CI**：基准版本不匹配会让闸门既不稳定又无意义；而做成软门控又不构成证明（前面 deny 那次已经证明了这点）。

**为什么不影响协议结论**：RPC 是给客户端的 API 面，**不在共识路径上**，缺失或多余的方法不可能导致分叉。它关系到客户端兼容性，与"协议实现是否正确"是不同问题。

### 一个可靠性教训

Rust 的 RPC 注册面是 `register_handlers()` 内的 `rpc_handlers![...]` 宏，右值有 `Self::f`、`module::f` 等多种形式，而 `middleware/rate_limiter.rs` 里还有同名字符串常量。**我用三版正则得到 46 / 51 / 57 三个不同答案**——在找到真实注册结构之前，任何一个数字都不可信。这也正是没把它做成闸门的第二个原因。
